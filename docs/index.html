CyberArk Secure Workload Access (SWA) — How It Works

Updated 2026-10-07 · Huy Do

Overview

SWA lets a workload read secrets without holding any credential: it proves which process it is on an attested machine, receives a short-lived SPIFFE JWT-SVID, and trades that JWT for a Secrets Manager access token.

  • Problem solved: the "secret zero" — no API key, password or certificate is stored with the application.

  • Identity = node identity (the machine, proven by an x509pop certificate) + workload identity (Unix user, binary path, binary sha256, matched by a policy).

  • Scope: how the parts fit, the four runtime flows, lifecycle events and the security model, as observed in the docker lab (SWA 1.1.4, Secrets Manager SaaS tenant, two environments prod and dev, two lab hosts sharing one tenant).

  • Lab repository: github.com/huydd79/test-swa-docker. Statements marked observed come from lab logs and API responses; statements marked inferred are not confirmed by vendor documentation.

Components and trust boundaries

Four parties take part, and only the tenant is trusted by everyone: it holds the policy, publishes the keys, and is the only place a verifier ever looks.

Numbers on the arrows are the flows described below. Each environment (prod, dev) repeats this picture with its own trust domain, CA, server, node group and authenticator.

Tenant object model

Everything SWA enforces is configured on the tenant; the SWA Server only caches and applies it. Objects nest under a trust domain, and Secrets Manager objects (authenticator, host, permissions) sit beside them.

  • The template must start with spiffe://{{ .trustdomain }}/{{ .nodegroup }}/; the rest may use attestor variables.

  • CEL variables: unix.user, unix.group, unix.path, unix.sha256 (strings), unix.uid, unix.gid (integers, written unix.uid == 1001).

  • The tenant does not validate field names inside CEL: a typo is saved and only fails at run time; an unknown variable in the template is rejected at save time (observed).

Flow 1 — Server bootstrap and key publication

The SWA Server, not any admin tool, puts its public keys on the tenant: it logs in as its server component, creates a fresh CA and signing key, and uploads both. The tenant then serves them from the trust domain's .well-known URLs.

What must exist before step 1 (done once by the admin):

  • Server login key pair. An RSA 2048 key is generated for the server (lab: openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048). Its public half is written as a JWKS: kty RSA, use sig, alg RS256, kid = first 16 hex characters of the sha256 of the DER public key. The private key stays on the server host.

  • Server component. The admin registers the component under the server group with authentication.type JWT, issuer (https://swa-server-<env>.<domain>), sub (swa-server-<env>), audience (conjur) and that JWKS. The tenant answers with authn_id: the full URL of a dedicated authenticator authn-jwt/swa-server-<env>-<8 hex>.

  • Bootstrap config for the server: controlPlane.url (tenant), auth.type jwt, authnID (the URL above), tokenPath (where the login JWT is read), syncInterval, listen addresses (apiAddr :8443 for agents, webAddr :8080 for health) and trustRootDir.

StepWhoWhat happens
1Host signerBuilds the login JWT — header alg RS256, kid; claims iss, sub, aud conjur, iat, nbf (30 s back), exp (+1 h), random jti — and signs it with the server login private key. Repeated every 30 min so a valid token is always on disk. On Kubernetes this step is replaced by a projected service-account token with audience conjur.
2Host signer → ServerThe JWT is written atomically to tokenPath (mounted read-only into the server). The server re-reads it whenever it needs to log in again.
3Server → TenantPOST to authnID with the JWT.
4Tenant → ServerThe tenant verifies the signature with the component's registered JWKS (by kid) and checks iss, sub, aud, exp. Success returns a short-lived access token for the server component's own host (host/component/swa/<uuid>/<uuid>).
5ServerGenerates, in process, a self-signed CA (written to trustRootDir, log writing self signed root CA certificate) and a JWT-SVID signing key of the type the trust domain demands (RSA_4096, signature RS512). Neither private key is ever exported.
6Server → TenantPOST /api/swa/v1/servergroups/ca-bundles with the CA certificate (log ServerCaBundleUploaded).
7Server → TenantPOST /api/swa/v1/servergroups/signingkeys with the public signing key and its kid (log KeyUploaded).
8TenantAdds the key to the trust domain JWKS and the CA to the trust domain bundle. The trust domain is derived from the authenticated component, so a server can only publish into its own trust domain. Keys of earlier starts stay listed for a while (observed: two kids after one restart).
9Server → TenantRequests the configuration of its server group: node groups, SPIFFE ID templates, registration policies. Repeated every syncInterval (lab 5 min).
10Tenant → ServerReturns the policies; the server caches them and starts serving agents on apiAddr. readyz on webAddr turns 200.

Result: GET <tenant>/api/swa/trust-domains/<td>/.well-known/jwks lists the server's signing key, .well-known/ca-bundles lists its CA, and the server is ready for Flow 2.

Flow 2 — Agent node attestation (x509pop)

Trust between agent and server is mutual and anchored on two different roots: the agent trusts the server because the tenant's CA bundle says so, and the server trusts the agent because its certificate chains to the server group CA.

What must exist before step 1:

  • Node attestation CA (admin, once per server group). A CA key pair is created outside SWA (lab: openssl req -x509 -newkey rsa:4096 -sha256 -days 365, basicConstraints CA:TRUE, keyUsage keyCertSign, cRLSign). Only the CA certificate is uploaded, into the server group's attestation.x509pop.ca_certificates. The CA private key stays with whoever enrols machines.

  • Machine key and certificate (once per machine — this is the agent's registration; there is no per-agent object on the tenant):

    1. The machine generates its own RSA key and a CSR with CN=<node group> (lab: openssl req -newkey rsa:2048 -subj /CN=ng-prod).

    2. The enrolment authority signs the CSR with the CA: a leaf with CA:FALSE, keyUsage digitalSignature (lab: 30 days). The signing CA is the node attestation CA above. The tenant and the SWA Server hold only its certificate, and no SWA component holds its private key. In practice this CA belongs to the organisation's internal PKI, typically a dedicated SWA sub-CA under the corporate root (for example AD CS, EJBCA or Vault PKI, with the key in an HSM). It is run by the PKI or infrastructure team, not by application teams or workload owners. Machines obtain certificates through a controlled enrolment process: manual approval, or automatic via SCEP, EST or ACME when a trusted provisioning system builds the machine. In a lab, openssl can stand in for the PKI: use the self-signed CA above and sign the CSR with openssl x509 -req -in x509pop.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 30 -sha256 -out x509pop.cert -extfile ext.cnf, where ext.cnf contains basicConstraints=critical,CA:FALSE and keyUsage=critical,digitalSignature. The CA key is then just a file on the lab host, so anyone who can read it can issue a valid agent.

    3. Key and certificate are placed in the agent config directory (x509pop.key, x509pop.cert). The private key should never leave the machine; the vendor's Ansible role that copies a pre-made key to the host is marked PoC-only. The certificate is created when the CA signs the CSR in step 2: the CA takes the machine's public key and CN from the CSR, adds validity and extensions, and signs with the CA private key. The issuer is the enrolment authority (PKI), which returns the certificate to the machine through the enrolment protocol or the provisioning system. It is stored in three places: (a) on the machine, next to the private key, which only the agent's user can read; (b) at the CA, as an issuance record for audit and revocation; (c) not on the tenant or the SWA Server, which keep no per-machine certificate and see it only when the agent attests. Before expiry the machine must obtain a new certificate through the same process. If it lapses, the agent is rejected at its next attestation. In the lab, key and certificate are created on the lab host and mounted into the workload container's agent config directory.

  • Agent install and config. Binary /opt/swa/bin/swa-agent from the release bundle, run as a supervised service (systemd unit, or a container entrypoint loop). Config: trustDomain.name; bootstrap.bundleSourceUrl = <tenant>/api/swa/trust-domains/<td>/.well-known/ca-bundles with insecure: false; servers[].addr = server API address; agent.socketPath; nodeAttestor: x509pop with key and cert paths; workload.attestors: unix with discover_workload_path: true. On Kubernetes the node attestor is k8s_psat or k8s_jwt instead and no certificate is issued.

  • What makes the agent valid. Only the enrolment above. The CA bundle URL (step 1) is public and holds only CA certificates, so it grants no identity. A machine with the bundle and the binary but no CA-signed key is rejected at steps 4–5 and gets no agent identity, socket or JWT-SVID. The CN is fixed by the CA at signing, so the machine cannot choose its own node group. Whoever holds the node attestation CA private key therefore decides which machines can run a valid agent.

StepWhoWhat happens
1Agent → TenantDownloads the trust domain CA bundle over ordinary public HTTPS (the tenant's web certificate is the only thing trusted at this point).
2Tenant → AgentThe bundle: the internal CA certificates uploaded by every server of the trust domain (Flow 1, step 6).
3Agent → ServerOpens TLS to servers[].addr and validates the server certificate against the bundle — so a fake server without a CA in the tenant bundle is rejected.
4Agent → Serverx509pop: sends its certificate and signs a server challenge with the machine private key, proving possession (challenge mechanism inferred from SPIFFE/SPIRE x509pop).
5ServerVerifies the certificate chain to a CA registered on its server group, the validity period and the possession proof.
6ServerReads the certificate CN and maps the machine to the node group of that name (ng-prod). A CN that names no node group gets no workload identities (inferred).
7Server → AgentIssues the agent its run-time identity; from now on agent and server talk mTLS, and the agent pushes bundle and key updates to its local watchers (log Broadcasting bundles, Broadcasting key sets). The agent then creates the Workload API socket (/run/swa-agent/api.sock).

Re-run of this flow: at every agent start, and after a server restart (new server CA → the agent fetches the bundle again; if that fails it exits with Trust recovery failed after retries and its supervisor restarts it).

Flow 3 — Workload attestation and JWT-SVID issuance

The workload presents nothing: the agent asks the kernel which process is on the other end of the socket, describes it, and the server decides from policy whether that process deserves an identity.

What must exist before step 1:

  • Node group policy on the tenant, synced to the server (Flow 1, steps 9–10): workload_type unix, the registration policies (CEL, elements OR'ed) and the SPIFFE ID template (default spiffe://<td>/<node group>/workload/<unix.user>).

  • The pinned binary. The admin computes sha256sum of the exact client binary that will call the Workload API and writes it into the policy. Any rebuild or patch of that file changes the hash and needs a policy update.

  • An attested agent (Flow 2) with its socket open, and the workload running as the expected user (lab: swa-demo-sa, uid 1001, shell nologin).

StepWhoWhat happens
1Workload → AgentThe client connects to unix:///run/swa-agent/api.sock and calls the SPIFFE Workload API FetchJWTSVID with audience conjur (lab client uses go-spiffe/v2). It sends no credential, no name, no token.
2AgentAsks the kernel for the peer of that socket connection (SO_PEERCRED): the PID, UID and GID of the connecting process — values the process cannot forge.
3AgentReads /proc/<PID> to resolve user and group names (unix.user, unix.uid, unix.group, unix.gid, one supplementary group). Needs root, or CAP_SYS_PTRACE in a container, to read another user's process.
4AgentResolves /proc/<PID>/exe to the executable path (unix.path) and hashes that file (unix.sha256); workload_size_limit: -1 hashes files of any size. The path is the binary that opened the socket — for a script calling the agent CLI it is /opt/swa/bin/swa-agent, for curl/python3 it is the interpreter.
5Agent → ServerSends the attributes over the mTLS channel from Flow 2, together with the node group the agent belongs to.
6ServerEvaluates each registration policy of that node group as a CEL expression over the attributes (unix.uid is an integer, names are strings). The first element that returns true wins; none → refusal.
7ServerRenders the SPIFFE ID from the template (lab: spiffe://prod.swa.example.com/ng-prod/workload/swa-demo-sa) and signs the JWT-SVID with its signing key from Flow 1, step 5 (log SVIDIssued).
8Server → AgentJWT-SVID: header alg RS512, kid of the signing key; claims sub = SPIFFE ID, aud = conjur, iss = <tenant>/api/swa/trust-domains/<td>, exp ≈ 5 min. Or the error no matching registration policy.
9Agent → WorkloadReturns the JWT-SVID on the socket; the workload keeps it in memory only and moves to Flow 4.

Inferred: whether steps 6–7 run on the server or on a policy cache inside the agent is not visible in the logs; the outcome and the log line SVIDIssued on the server are observed.

Flow 4 — From JWT-SVID to a secret

Secrets Manager never talks to the SWA Server: it verifies the JWT-SVID with the keys the tenant itself publishes, maps the SPIFFE ID to a host, and returns only the variables that host is permitted to read.

What must exist before step 1:

  • Workload authenticator authn-jwt/<svc> (lab swa-prod), created by policy under conjur/authn-jwt and enabled: a webservice, a group apps with read, authenticate on it, and three variables — jwks-uri = <tenant>/api/swa/trust-domains/<td>/.well-known/jwks, issuer = <tenant>/api/swa/trust-domains/<td>, audience = conjur. No token-app-property is set: the host is named in the URL (host-in-URL mode).

  • Workload host. Created by the tenant itself the first time a JWT-SVID is issued for a SPIFFE ID: data/swa/trust-domains/<td>/workloads/<SPIFFE ID>. The admin then adds:

    1. the annotation authn-jwt/<svc>/sub: <SPIFFE ID> on the host;

    2. a grant of the host into conjur/authn-jwt/<svc>/apps (loaded in that branch);

    3. !permit with read, execute on each variable the workload may read, loaded in the safe's branch data/vault/<safe>.

StepWhoWhat happens
1Workload → Secrets ManagerPOST <tenant>/api/authn-jwt/<svc>/conjur/<url-encoded host id>/authenticate with form body jwt=<JWT-SVID>. Host id = host/data/swa/trust-domains/<td>/workloads/<SPIFFE ID>.
2Secrets Manager → JWKSFetches the key set from the authenticator's jwks-uri (the trust domain's public .well-known/jwks).
3JWKS → Secrets ManagerReturns the public keys uploaded by the servers of that trust domain (Flow 1, step 7). The JWT header kid selects one.
4Secrets ManagerVerifies the RS512 signature with that key, then iss equals the configured issuer, aud contains conjur, exp/nbf are valid. A JWT from another trust domain fails here (other issuer, other keys) → 401.
5Secrets ManagerChecks the host named in the URL: it exists, it is a member of apps of this authenticator, and its annotation authn-jwt/<svc>/sub equals the JWT sub. Any mismatch → 401.
6Secrets Manager → WorkloadReturns an access token for that host (base64 JSON token, short-lived).
7Workload → Secrets ManagerGET <tenant>/api/secrets/conjur/variable/<url-encoded variable id> with header Authorization: Token token="<base64 token>", e.g. data/vault/<safe>/<account>/password.
8Secrets ManagerChecks that the host has execute (fetch value) on that variable through a direct permit or a group.
9Secrets Manager → WorkloadThe secret value, or HTTP 404 when the host has no privilege (the variable is not even revealed to exist).

Nothing in this flow touches the SWA Server or the agent: Secrets Manager trusts the JWT-SVID only because the tenant publishes the signing keys. The workload holds the JWT-SVID (~5 min) and the access token (minutes) in memory only.

Lifecycle and rotation

Every SWA Server start repeats the whole bootstrap: new login, new internal CA, new signing key, both uploaded again. Verifiers and agents follow automatically; nothing is reconfigured by hand.

Security model

A workload is only as trustworthy as the three keys behind it: the node-attestation CA key, the SWA Server's signing key, and tenant admin rights. Protect those; the workload itself holds nothing worth stealing.

AssetWho holds itIf compromised
x509pop CA key (state/<env>/pki/ca.key)Whoever enrols machinesAttacker issues a cert with any CN and joins any node group of that server group
Server login key (state/<env>/signer/jwt.key)SWA Server hostAttacker logs in as the server component and uploads its own signing key
Server internal signing keySWA Server process (regenerated each start; storage not documented)Attacker mints JWT-SVIDs for any SPIFFE ID in the trust domain until the key leaves the JWKS
Tenant adminTenant administratorsAttacker edits policies, JWKS, permissions: full control
Root on a workload nodeNode administratorCan replace binaries (new hash → denied) but can run the pinned binary as the service user and read what it reads
JWT-SVID / access tokenThe workload, minutesBearer tokens: usable by whoever holds them until expiry (JWT-SVID 5 min)

Lab tests on both hosts confirm each enforcement point:

  • Another user (root) running the pinned client → no matching registration policy.

  • The client with one byte changed → no matching registration policy (sha256 pin).

  • prod workload reading a dev secret → HTTP 404 (no permission).

  • A prod JWT-SVID sent to the dev authenticator → HTTP 401 (other issuer and JWKS).

Limits to keep in mind:

  • Hash pinning only works for a compiled binary that opens the agent socket itself. A script calling the swa-agent CLI is attested as swa-agent; a script talking to the socket via curl or python3 is attested as that interpreter. Editing the script changes nothing in the attestation.

  • Policy element 2 (agent CLI) is a deliberate hole for the demo: any process of swa-demo-sa can get a JWT through the CLI. Remove it outside demos; until then the matrix row "swa-agent CLI → DENY" is not a meaningful check.

  • The node group is chosen by the certificate CN. Nothing else stops a machine from joining an existing node group, so the CA key and the enrolment process are the control point; separate server groups (separate CAs) per environment, as in the lab, limit the blast radius.

  • Only one supplementary group is reported (unix.supplementary_group equals the primary group), so policies cannot rely on secondary groups such as wheel (observed).

  • The agent runs as root and needs CAP_SYS_PTRACE in a container to read other users' /proc entries.

Hardening for production: keep the CA key offline or in a PKI (sign CSRs, never copy the key to nodes), run the service user with nologin and no sudo, start workloads from systemd (User=), drop the CLI policy element, and alert on tenant policy changes.

Scaling out

Adding a machine needs no tenant change: it needs an agent, a certificate signed by the server group CA with the right node-group CN, and network reach to a SWA Server.

  1. The machine runs the SWA Agent as root.

  2. The machine creates a key and CSR with CN=<node group>; an enrolment authority signs it with the server group CA. The CA key never leaves that authority.

  3. The agent is configured with the trust domain name, the tenant bundle URL (.well-known/ca-bundles), the server address, its x509pop key and certificate, and the unix workload attestor.

  4. Workloads of the same user on that machine get the same SPIFFE ID as on every other machine of the node group (the default ID has no host part), so they share one Secrets Manager host and its permissions.

NeedHow in this design
Tell machines apartSeparate node groups (different CN) or a SPIFFE ID template with more attributes; hostname is not an attestor variable in the unix attestor (observed variable list)
Separate environmentsSeparate trust domains + server groups + CAs (prod, dev) and per-environment authenticators
Several lab hosts on one tenantLAB_ID in config.env: trust domain prod.<LAB_ID>.swa.<domain>, authenticator swa-prod-<LAB_ID>; tested with lab2 on Ubuntu 24.04 next to the original lab
AutoscalingIssue the node certificate at boot from a PKI/enrolment service (CSR signed automatically); the CA key never ships in the image
Agent behind a proxyAgent → server is gRPC over TLS on the server API port; the agent must reach addr and the tenant bundle URL
Server on KubernetesSame bootstrap, but the server logs in with its projected service-account token instead of a self-signed JWT

Naming tip: keep SPIFFE paths about what the workload is (environment, node group, service account), not where it runs, so permissions survive machine replacement.
