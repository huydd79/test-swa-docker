CyberArk Secure Workload Access (SWA) — หลักการทำงาน

อัปเดต 2026-10-11 · Huy Do

ภาพรวม

SWA ช่วยให้ workload อ่าน secret ได้โดยไม่ต้องถือ credential ใดๆ: workload พิสูจน์ว่าตนเองคือ process ใดบนเครื่องที่ผ่าน attestation แล้ว ได้รับ SPIFFE JWT-SVID อายุสั้น จากนั้นนำ JWT นั้นไปแลกเป็น access token ของ Secrets Manager

  • ปัญหาที่แก้: "secret zero" — ไม่มี API key, รหัสผ่าน หรือ certificate ใดถูกจัดเก็บไว้กับแอปพลิเคชัน

  • Identity = node identity (ตัวเครื่อง พิสูจน์ด้วย certificate แบบ x509pop) + workload identity (Unix user, binary path, sha256 ของ binary ซึ่งจับคู่ด้วย policy)

  • ขอบเขต: องค์ประกอบต่างๆ ทำงานร่วมกันอย่างไร, runtime flow ทั้งสี่, เหตุการณ์ใน lifecycle และ security model ตามที่สังเกตได้ใน lab: SWA 1.1.4, SWA Server deploy ด้วย helm chart ของ vendor บน k3s cluster แบบ single-node ที่รันอยู่ภายใน Docker container, SWA Agent และ workload อยู่ใน Docker container ธรรมดา (หนึ่ง container ต่อหนึ่งเครื่องจำลอง), Secrets Manager SaaS tenant หนึ่งตัว และสอง environment คือ prod และ dev; lab host หลายเครื่องสามารถใช้ tenant ร่วมกันได้

  • Lab repository: github.com/huydd79/test-swa-docker ข้อความที่ระบุว่า สังเกตได้จริง (observed) มาจาก log และ API response ของ lab; ข้อความที่ระบุว่า อนุมาน (inferred) ยังไม่ได้รับการยืนยันจากเอกสารของ vendor

องค์ประกอบและขอบเขตความเชื่อถือ (trust boundary)

มีสี่ฝ่ายที่เกี่ยวข้อง และมีเพียง tenant เท่านั้นที่ทุกฝ่ายเชื่อถือ: tenant ถือ policy, เผยแพร่ key และเป็นแหล่งเดียวที่ verifier ใช้ตรวจสอบ

ตัวเลขบนลูกศรคือ flow ที่อธิบายด้านล่าง แต่ละ environment (prod, dev) มีโครงสร้างแบบเดียวกันนี้ซ้ำ โดยมี trust domain, CA, server, node group และ authenticator เป็นของตัวเอง

Node group policy ที่ใช้ใน lab (element ใน array เชื่อมกันด้วย OR, ภายใน element เดียวใช้ &&):

workload_type: unix
workload_registration_policies:
  1. unix.user == "swa-demo-sa" && unix.sha256 == "<sha256 of swa-go-test>"
  2. unix.user == "swa-demo-sa" && unix.path  == "/opt/swa/bin/swa-agent"   # demo only
# no spiffe_id_template set -> default ID observed: spiffe://<trust domain>/<node group>/workload/<unix.user>
# workload authenticator variables: jwks-uri = <tenant>/api/swa/trust-domains/<td>/.well-known/jwks,
#                                   issuer   = <tenant>/api/swa/trust-domains/<td>, audience = conjur

  • Template ต้องขึ้นต้นด้วย spiffe://{{ .trustdomain }}/{{ .nodegroup }}/; ส่วนที่เหลือสามารถใช้ตัวแปรของ attestor ได้

  • ตัวแปร CEL: unix.user, unix.group, unix.path, unix.sha256 (string), unix.uid, unix.gid (integer, เขียนเป็น unix.uid == 1001)

  • Tenant ไม่ตรวจสอบชื่อ field ภายใน CEL: หากพิมพ์ผิดจะยังบันทึกได้และจะ fail ตอน runtime เท่านั้น; แต่ตัวแปรที่ไม่รู้จักใน template จะถูกปฏิเสธตั้งแต่ตอนบันทึก (สังเกตได้จริง)

Flow 1 — การ bootstrap ของ server และการเผยแพร่ key

SWA Server เป็นผู้นำ public key ของตนขึ้นไปไว้บน tenant เอง ไม่ใช่เครื่องมือของ admin: server login ในฐานะ server component ของตน สร้าง CA และ signing key ชุดใหม่ แล้วอัปโหลดทั้งสองอย่าง จากนั้น tenant จะให้บริการ key เหล่านี้ผ่าน URL .well-known ของ trust domain

สิ่งที่ต้องมีก่อนขั้นตอนที่ 1 (admin ทำเพียงครั้งเดียว):

  • Login identity ของ server Server รันในฐานะ service account swa-server ใน namespace swa-<env> k3s จะ mount projected service-account token ให้ (audience conjur, 1 ชม., kubelet เป็นผู้ rotate) ซึ่งลงนามด้วย service-account key ของ cluster (RS256) ส่วน public คือ JWKS ของ cluster (kubectl get --raw /openid/v1/jwks) และ issuer คือ https://kubernetes.default.svc.cluster.local Private key ไม่เคยออกจาก k3s (lab: key อยู่ใน Docker volume swa-k3s ดังนั้นการสร้าง container ใหม่จะยังคงใช้ key เดิม)

  • Server component Admin ลงทะเบียน component ภายใต้ server group โดยระบุ authentication.type JWT, issuer (issuer ของ k3s), sub (system:serviceaccount:swa-<env>:swa-server), audience (conjur) และ JWKS ของ cluster เนื่องจาก SaaS tenant เข้าถึง k3s API ไม่ได้ จึงลงทะเบียน JWKS แบบ inline (public_keys) แทนการใช้ jwks_uri Tenant ตอบกลับด้วย authn_id ซึ่งเป็น URL เต็มของ authenticator เฉพาะ authn-jwt/swa-server-<env>-<8 hex> หาก key ของ cluster เปลี่ยน (สร้าง cluster ใหม่) component จะถูกลบและลงทะเบียนใหม่ ซึ่งจะได้ authn_id ใหม่ และ tenant จะลบ authenticator เดิมเอง (สังเกตได้จริง)

  • Bootstrap config ของ server ซึ่ง helm chart render เป็น ConfigMap จาก controlPlane.url, controlPlane.auth.authnID และ controlPlane.auth.audience: controlPlane.url (tenant), auth.type jwt, authnID (URL ข้างต้น), tokenPath (projected token, /var/run/secrets/tokens/swa-token), syncInterval (15 นาทีใน chart 0.1.0), listen address (apiAddr :8443 สำหรับ agent, webAddr :8080 สำหรับ health) และ trustRootDir

2k3s → ServerToken ถูก mount แบบ read-only ที่ tokenPath (projected volume) Server จะอ่านไฟล์ใหม่ทุกครั้งที่ต้อง login อีกครั้ง
3Server → TenantPOST ไปยัง authnID พร้อม JWT
4Tenant → ServerTenant ตรวจสอบ signature ด้วย JWKS ที่ลงทะเบียนไว้ของ component (เลือกตาม kid) และตรวจ iss, sub, aud, exp หากสำเร็จจะคืน access token อายุสั้นสำหรับ host ของ server component เอง (host/component/swa/<uuid>/<uuid>)

10Tenant → Serverคืน policy; server เก็บ cache และเริ่มให้บริการ agent บน apiAddr และ readyz บน webAddr จะเปลี่ยนเป็น 200

ผลลัพธ์: GET <tenant>/api/swa/trust-domains/<td>/.well-known/jwks แสดง signing key ของ server, .well-known/ca-bundles แสดง CA ของ server และ server พร้อมสำหรับ Flow 2

Flow 2 — Node attestation ของ agent (x509pop)

ความเชื่อถือระหว่าง agent และ server เป็นแบบสองทาง และยึดโยงกับ root ที่ต่างกันสองตัว: agent เชื่อถือ server เพราะ CA bundle ของ tenant ระบุไว้ และ server เชื่อถือ agent เพราะ certificate ของ agent chain ไปยัง CA ของ server group

สิ่งที่ต้องมีก่อนขั้นตอนที่ 1:

  • Node attestation CA (admin ทำครั้งเดียวต่อ server group) CA key pair ถูกสร้างนอก SWA (lab: openssl req -x509 -newkey rsa:4096 -sha256 -days 365, basicConstraints CA:TRUE, keyUsage keyCertSign, cRLSign) อัปโหลดเฉพาะ CA certificate ไปยัง attestation.x509pop.ca_certificates ของ server group ส่วน CA private key จะอยู่กับผู้ที่ทำ enrolment ให้เครื่อง

  • Machine key และ certificate (ครั้งเดียวต่อเครื่อง — นี่คือการลงทะเบียน agent; บน tenant ไม่มี object แยกต่อ agent):

    1. เครื่องสร้าง RSA key ของตนเองและ CSR ที่มี CN=<node group> (lab: openssl req -newkey rsa:2048 -subj /CN=ng-prod)

    2. Enrolment authority ลงนาม CSR ด้วย CA ได้เป็น leaf certificate ที่มี CA:FALSE, keyUsage digitalSignature (lab: 30 วัน) CA ที่ใช้ลงนามคือ node attestation CA ข้างต้น Tenant และ SWA Server ถือเพียง certificate ของ CA นี้ และไม่มีองค์ประกอบใดของ SWA ถือ private key ของมัน ในทางปฏิบัติ CA นี้เป็นส่วนหนึ่งของ PKI ภายในองค์กร โดยทั่วไปเป็น SWA sub-CA เฉพาะภายใต้ corporate root (เช่น AD CS, EJBCA หรือ Vault PKI โดยเก็บ key ไว้ใน HSM) ดูแลโดยทีม PKI หรือทีม infrastructure ไม่ใช่ทีมแอปพลิเคชันหรือเจ้าของ workload เครื่องจะได้รับ certificate ผ่านกระบวนการ enrolment ที่มีการควบคุม: อนุมัติด้วยมือ หรืออัตโนมัติผ่าน SCEP, EST หรือ ACME เมื่อระบบ provisioning ที่เชื่อถือได้เป็นผู้สร้างเครื่อง ใน lab สามารถใช้ openssl แทน PKI ได้ โดยใช้ self-signed CA ข้างต้นและลงนาม CSR ด้วย openssl x509 -req -in x509pop.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 30 -sha256 -out x509pop.cert -extfile ext.cnf ซึ่ง ext.cnf มี basicConstraints=critical,CA:FALSE และ keyUsage=critical,digitalSignature ในกรณีนี้ CA key เป็นเพียงไฟล์บน lab host ดังนั้นใครก็ตามที่อ่านไฟล์นี้ได้ก็สามารถออก agent ที่ valid ได้

    3. Key และ certificate ถูกวางไว้ใน config directory ของ agent (x509pop.key, x509pop.cert) Private key ไม่ควรออกจากเครื่อง; Ansible role ของ vendor ที่คัดลอก key ที่สร้างไว้ล่วงหน้าไปยัง host ถูกระบุว่าใช้สำหรับ PoC เท่านั้น Certificate ถูกสร้างขึ้นเมื่อ CA ลงนาม CSR ในขั้นตอนที่ 2: CA นำ public key และ CN ของเครื่องจาก CSR มาเพิ่มช่วงอายุการใช้งานและ extension แล้วลงนามด้วย CA private key ผู้ออก certificate คือ enrolment authority (PKI) ซึ่งส่ง certificate กลับไปยังเครื่องผ่าน enrolment protocol หรือระบบ provisioning Certificate ถูกเก็บไว้สามแห่ง: (a) บนเครื่อง ข้างๆ private key ซึ่งมีเพียง user ของ agent เท่านั้นที่อ่านได้; (b) ที่ CA ในรูปแบบบันทึกการออก certificate เพื่อใช้ audit และ revoke; (c) ไม่อยู่บน tenant หรือ SWA Server ซึ่งไม่เก็บ certificate รายเครื่อง และจะเห็น certificate เฉพาะตอนที่ agent ทำ attestation เท่านั้น ก่อนหมดอายุ เครื่องต้องขอ certificate ใหม่ผ่านกระบวนการเดียวกัน หากหมดอายุ agent จะถูกปฏิเสธใน attestation ครั้งถัดไป ใน lab key และ certificate ถูกสร้างบน lab host และ mount เข้าไปใน config directory ของ agent ภายใน workload container

  • การติดตั้งและ config ของ agent Binary /opt/swa/bin/swa-agent จาก release bundle รันเป็น service ภายใต้ supervisor (systemd unit หรือ loop ใน container entrypoint) Config: trustDomain.name; bootstrap.bundleSourceUrl = <tenant>/api/swa/trust-domains/<td>/.well-known/ca-bundles พร้อม insecure: false; servers[].addr = address ของ server API (lab: host.docker.internal:<port> บน macOS หรือ Docker bridge gateway บน Linux ซึ่ง k3s container publish ไปยัง NodePort ของ server); agent.socketPath; nodeAttestor: x509pop พร้อม path ของ key และ cert; workload.attestors: unix พร้อม discover_workload_path: true บน Kubernetes จะใช้ node attestor เป็น k8s_psat หรือ k8s_jwt แทน และไม่มีการออก certificate

  • สิ่งที่ทำให้ agent valid มีเพียงการ enrolment ข้างต้นเท่านั้น CA bundle URL (ขั้นตอนที่ 1) เป็น public และมีเพียง CA certificate จึงไม่ได้มอบ identity ใดๆ เครื่องที่มี bundle และ binary แต่ไม่มี key ที่ CA ลงนามจะถูกปฏิเสธในขั้นตอนที่ 4–5 และไม่ได้รับ agent identity, socket หรือ JWT-SVID CN ถูกกำหนดตายตัวโดย CA ตอนลงนาม เครื่องจึงไม่สามารถเลือก node group เองได้ ดังนั้นผู้ที่ถือ private key ของ node attestation CA จึงเป็นผู้ตัดสินว่าเครื่องใดสามารถรัน agent ที่ valid ได้

1Agent → Tenantดาวน์โหลด CA bundle ของ trust domain ผ่าน HTTPS สาธารณะตามปกติ (ณ จุดนี้สิ่งเดียวที่เชื่อถือคือ web certificate ของ tenant)
2Tenant → AgentBundle: internal CA certificate ที่ server ทุกตัวของ trust domain อัปโหลดไว้ (Flow 1, ขั้นตอนที่ 6)
3Agent → Serverเปิด TLS ไปยัง servers[].addr และตรวจสอบ server certificate กับ bundle — ดังนั้น server ปลอมที่ไม่มี CA อยู่ใน bundle ของ tenant จะถูกปฏิเสธ
4Agent → Serverx509pop: ส่ง certificate ของตนและลงนาม challenge จาก server ด้วย private key ของเครื่อง เพื่อพิสูจน์การครอบครอง key (กลไก challenge อนุมานจาก x509pop ของ SPIFFE/SPIRE)
5Serverตรวจสอบ certificate chain ไปยัง CA ที่ลงทะเบียนไว้ใน server group ของตน, ช่วงอายุการใช้งาน และหลักฐานการครอบครอง key
6Serverอ่าน CN ของ certificate และจับคู่เครื่องกับ node group ที่มีชื่อนั้น (ng-prod) CN ที่ไม่ตรงกับ node group ใดจะไม่ได้รับ workload identity (อนุมาน)
7Server → Agentออก run-time identity ให้ agent; นับจากนี้ agent และ server สื่อสารกันด้วย mTLS และ agent จะ push การอัปเดต bundle และ key ไปยัง watcher ภายในเครื่อง (log Broadcasting bundles, Broadcasting key sets) จากนั้น agent จะสร้าง Workload API socket (/run/swa-agent/api.sock)

Flow นี้จะทำงานซ้ำทุกครั้งที่ agent เริ่มทำงาน และหลัง server restart (CA ของ server เปลี่ยน → agent ดึง bundle ใหม่; หากไม่สำเร็จจะ exit พร้อม Trust recovery failed after retries และ supervisor จะ restart ให้)

Flow 3 — Workload attestation และการออก JWT-SVID

Workload ไม่ต้องแสดงสิ่งใดเลย: agent สอบถาม kernel ว่า process ใดอยู่อีกฝั่งของ socket อธิบายคุณลักษณะของ process นั้น แล้ว server ตัดสินจาก policy ว่า process นั้นสมควรได้รับ identity หรือไม่

สิ่งที่ต้องมีก่อนขั้นตอนที่ 1:

  • Node group policy บน tenant ที่ sync ไปยัง server แล้ว (Flow 1, ขั้นตอนที่ 9–10): workload_type unix, registration policy (CEL, element เชื่อมกันด้วย OR) และ SPIFFE ID template (ค่า default spiffe://<td>/<node group>/workload/<unix.user>)

  • Binary ที่ถูก pin Admin คำนวณ sha256sum ของ client binary ตัวที่จะเรียก Workload API จริง แล้วเขียนลงใน policy การ rebuild หรือ patch ไฟล์นั้นไม่ว่าแบบใดจะทำให้ hash เปลี่ยนและต้องอัปเดต policy

  • Agent ที่ผ่าน attestation แล้ว (Flow 2) ซึ่งเปิด socket ไว้ และ workload รันในฐานะ user ที่กำหนด (lab: swa-demo-sa, uid 1001, shell nologin)

ขั้นตอนผู้ดำเนินการสิ่งที่เกิดขึ้น
1Workload → AgentClient เชื่อมต่อไปยัง unix:///run/swa-agent/api.sock และเรียก SPIFFE Workload API FetchJWTSVID ด้วย audience conjur (client ใน lab ใช้ go-spiffe/v2) โดยไม่ส่ง credential, ชื่อ หรือ token ใดๆ
2Agentสอบถาม kernel ถึง peer ของการเชื่อมต่อ socket นั้น (SO_PEERCRED): PID, UID และ GID ของ process ที่เชื่อมต่อเข้ามา — ซึ่งเป็นค่าที่ process ไม่สามารถปลอมแปลงได้
3Agentอ่าน /proc/<PID> เพื่อหาชื่อ user และ group (unix.user, unix.uid, unix.group, unix.gid, supplementary group หนึ่งกลุ่ม) ต้องใช้สิทธิ์ root หรือ CAP_SYS_PTRACE ใน container เพื่ออ่าน process ของ user อื่น
4AgentResolve /proc/<PID>/exe เป็น path ของ executable (unix.path) และ hash ไฟล์นั้น (unix.sha256); workload_size_limit: -1 ทำให้ hash ไฟล์ได้ทุกขนาด Path คือ binary ที่เปิด socket — สำหรับ script ที่เรียก agent CLI จะเป็น /opt/swa/bin/swa-agent ส่วน curl/python3 จะเป็นตัว interpreter
5Agent → Serverส่ง attribute ผ่าน mTLS channel จาก Flow 2 พร้อมกับ node group ที่ agent สังกัด
6Serverประเมิน registration policy แต่ละข้อของ node group นั้นเป็น CEL expression บน attribute (unix.uid เป็น integer, ชื่อเป็น string) element แรกที่คืนค่า true จะถูกใช้; หากไม่มีข้อใดตรง → ปฏิเสธ
7ServerRender SPIFFE ID จาก template (lab: spiffe://prod.swa.example.com/ng-prod/workload/swa-demo-sa) และลงนาม JWT-SVID ด้วย signing key จาก Flow 1 ขั้นตอนที่ 5 (log SVIDIssued)
8Server → AgentJWT-SVID: header alg RS512, kid ของ signing key; claim sub = SPIFFE ID, aud = conjur, iss = <tenant>/api/swa/trust-domains/<td>, exp ≈ 5 นาที หรือ error no matching registration policy
9Agent → Workloadคืน JWT-SVID ผ่าน socket; workload เก็บไว้ในหน่วยความจำเท่านั้นและไปต่อที่ Flow 4

อนุมาน: ไม่สามารถเห็นจาก log ได้ว่าขั้นตอนที่ 6–7 ทำงานบน server หรือบน policy cache ภายใน agent; ส่วนผลลัพธ์และ log บรรทัด SVIDIssued บน server เป็นสิ่งที่สังเกตได้จริง

Flow 4 — จาก JWT-SVID สู่ secret

Secrets Manager ไม่เคยติดต่อกับ SWA Server: Secrets Manager ตรวจสอบ JWT-SVID ด้วย key ที่ tenant เผยแพร่เอง จับคู่ SPIFFE ID กับ host และคืนค่าเฉพาะ variable ที่ host นั้นได้รับอนุญาตให้อ่านเท่านั้น

สิ่งที่ต้องมีก่อนขั้นตอนที่ 1:

  • Workload authenticator authn-jwt/<svc> (lab swa-prod) สร้างด้วย policy ภายใต้ conjur/authn-jwt และ enable แล้ว ประกอบด้วย webservice, group apps ที่มีสิทธิ์ read, authenticate บน webservice นั้น และ variable สามตัว — jwks-uri = <tenant>/api/swa/trust-domains/<td>/.well-known/jwks, issuer = <tenant>/api/swa/trust-domains/<td>, audience = conjur ไม่ได้ตั้งค่า token-app-property: host ถูกระบุใน URL (โหมด host-in-URL)

  • Workload host Tenant สร้างขึ้นเองในครั้งแรกที่มีการออก JWT-SVID สำหรับ SPIFFE ID นั้น: data/swa/trust-domains/<td>/workloads/<SPIFFE ID> จากนั้น admin เพิ่ม:

    1. annotation authn-jwt/<svc>/sub: <SPIFFE ID> บน host;

    2. grant host เข้าไปใน conjur/authn-jwt/<svc>/apps (load ใน branch นั้น);

    3. !permit ด้วย read, execute บนแต่ละ variable ที่ workload อ่านได้ โดย load ใน branch ของ safe data/vault/<safe>

ขั้นตอนผู้ดำเนินการสิ่งที่เกิดขึ้น
1Workload → Secrets ManagerPOST <tenant>/api/authn-jwt/<svc>/conjur/<url-encoded host id>/authenticate พร้อม form body jwt=<JWT-SVID> Host id = host/data/swa/trust-domains/<td>/workloads/<SPIFFE ID>
2Secrets Manager → JWKSดึง key set จาก jwks-uri ของ authenticator (.well-known/jwks สาธารณะของ trust domain)
3JWKS → Secrets Managerคืน public key ที่ server ของ trust domain นั้นอัปโหลดไว้ (Flow 1, ขั้นตอนที่ 7) โดย kid ใน JWT header เป็นตัวเลือก key
4Secrets Managerตรวจสอบ RS512 signature ด้วย key นั้น จากนั้นตรวจว่า iss ตรงกับ issuer ที่กำหนด, aud มี conjur และ exp/nbf ยัง valid JWT จาก trust domain อื่นจะ fail ที่ขั้นตอนนี้ (issuer ต่างกัน, key ต่างกัน) → 401
5Secrets Managerตรวจสอบ host ที่ระบุใน URL: ต้องมีอยู่จริง, เป็นสมาชิกของ apps ของ authenticator นี้ และ annotation authn-jwt/<svc>/sub ต้องตรงกับ sub ใน JWT หากไม่ตรงข้อใด → 401
6Secrets Manager → Workloadคืน access token สำหรับ host นั้น (token แบบ JSON เข้ารหัส base64, อายุสั้น)
7Workload → Secrets ManagerGET <tenant>/api/secrets/conjur/variable/<url-encoded variable id> พร้อม header Authorization: Token token="<base64 token>" เช่น data/vault/<safe>/<account>/password
8Secrets Managerตรวจว่า host มีสิทธิ์ execute (ดึงค่า) บน variable นั้น ผ่าน permit โดยตรงหรือผ่าน group
9Secrets Manager → Workloadค่า secret หรือ HTTP 404 เมื่อ host ไม่มีสิทธิ์ (ไม่เปิดเผยแม้กระทั่งว่า variable นั้นมีอยู่)

ไม่มีส่วนใดใน flow นี้ที่เกี่ยวข้องกับ SWA Server หรือ agent: Secrets Manager เชื่อถือ JWT-SVID เพียงเพราะ tenant เป็นผู้เผยแพร่ signing key Workload เก็บ JWT-SVID (~5 นาที) และ access token (ไม่กี่นาที) ไว้ในหน่วยความจำเท่านั้น

Security model

Workload จะน่าเชื่อถือได้เพียงใดขึ้นอยู่กับ key สามอย่างที่อยู่เบื้องหลัง: node-attestation CA key, signing key ของ SWA Server และสิทธิ์ admin ของ tenant ให้ปกป้องสิ่งเหล่านี้; ตัว workload เองไม่ได้ถือสิ่งใดที่คุ้มค่าแก่การขโมย

Assetผู้ถือครองหากถูก compromise
x509pop CA key (state/<env>/pki/ca.key)ผู้ที่ทำ enrolment ให้เครื่องผู้โจมตีออก cert ด้วย CN ใดก็ได้และเข้าร่วม node group ใดก็ได้ของ server group นั้น
k3s service-account signing key (Docker volume swa-k3s)k3s cluster กล่าวคือใครก็ตามที่ควบคุม Docker บน hostผู้โจมตีสร้าง token สำหรับ system:serviceaccount:swa-<env>:swa-server login เป็น server component และอัปโหลด signing key ของตนเอง
Internal signing key ของ serverProcess ของ SWA Server (สร้างใหม่ทุกครั้งที่เริ่ม; ไม่มีเอกสารระบุการจัดเก็บ)ผู้โจมตีสร้าง JWT-SVID สำหรับ SPIFFE ID ใดก็ได้ใน trust domain จนกว่า key จะถูกนำออกจาก JWKS
Tenant adminผู้ดูแลระบบ tenantผู้โจมตีแก้ไข policy, JWKS, permission ได้: ควบคุมได้ทั้งหมด
Root บน workload nodeผู้ดูแล nodeเปลี่ยน binary ได้ (hash ใหม่ → ถูกปฏิเสธ) แต่สามารถรัน binary ที่ถูก pin ในฐานะ service user และอ่านสิ่งที่ binary นั้นอ่านได้
JWT-SVID / access tokenWorkload, ไม่กี่นาทีBearer token: ใครถือก็ใช้ได้จนกว่าจะหมดอายุ (JWT-SVID 5 นาที)

การทดสอบใน lab บนทั้งสอง host ยืนยันจุดบังคับใช้แต่ละจุด:

  • User อื่น (root) รัน client ที่ถูก pin → no matching registration policy

  • Client ที่ถูกแก้ไขหนึ่ง byte → no matching registration policy (sha256 pin)

  • Workload prod อ่าน secret ของ dev → HTTP 404 (ไม่มีสิทธิ์)

  • JWT-SVID ของ prod ที่ส่งไปยัง authenticator ของ dev → HTTP 401 (issuer และ JWKS ต่างกัน)

ข้อจำกัดที่ควรคำนึงถึง:

  • Hash pinning ใช้ได้เฉพาะกับ compiled binary ที่เปิด agent socket เองเท่านั้น Script ที่เรียก swa-agent CLI จะถูก attest เป็น swa-agent; script ที่คุยกับ socket ผ่าน curl หรือ python3 จะถูก attest เป็น interpreter นั้น การแก้ไข script จึงไม่มีผลใดๆ ต่อ attestation

  • Policy element ที่ 2 (agent CLI) เป็นช่องโหว่ที่จงใจเปิดไว้สำหรับ demo: process ใดๆ ของ swa-demo-sa สามารถขอ JWT ผ่าน CLI ได้ ให้ลบออกเมื่อไม่ได้ใช้ demo; จนกว่าจะลบ test matrix จะคาดหวัง "swa-demo-sa + swa-agent CLI → OK" (ช่องโหว่) และ "root + swa-agent CLI → DENY"

  • Node group ถูกเลือกโดย CN ของ certificate ไม่มีสิ่งอื่นใดป้องกันเครื่องจากการเข้าร่วม node group ที่มีอยู่ ดังนั้น CA key และกระบวนการ enrolment จึงเป็นจุดควบคุม; การแยก server group (แยก CA) ตาม environment ดังเช่นใน lab ช่วยจำกัดขอบเขตความเสียหาย (blast radius)

  • มีการรายงาน supplementary group เพียงกลุ่มเดียว (unix.supplementary_group เท่ากับ primary group) ดังนั้น policy จึงพึ่งพา secondary group เช่น wheel ไม่ได้ (สังเกตได้จริง)

  • Agent รันเป็น root และต้องใช้ CAP_SYS_PTRACE ใน container เพื่ออ่าน entry ใน /proc ของ user อื่น

  • k3s รันเป็น privileged container ใครก็ตามที่เข้าถึง Docker บน lab host ได้จะควบคุม cluster, service-account key และด้วยเหตุนี้จึงควบคุม identity ของ server ได้ด้วย นอก lab ให้ใช้ cluster จริงที่จำกัดการเข้าถึง

Hardening สำหรับ production: เก็บ CA key แบบ offline หรือไว้ใน PKI (ลงนาม CSR, ห้ามคัดลอก key ไปยัง node), รัน service user ด้วย nologin และไม่มี sudo, เริ่ม workload จาก systemd (User=), ตัด CLI policy element ออก และตั้ง alert เมื่อมีการเปลี่ยน policy บน tenant

การขยายระบบ (Scaling out)

การเพิ่มเครื่องไม่ต้องเปลี่ยนแปลงสิ่งใดบน tenant: ต้องการเพียง agent, certificate ที่ลงนามโดย CA ของ server group พร้อม CN ของ node group ที่ถูกต้อง และเส้นทางเครือข่ายที่เข้าถึง SWA Server ได้

  1. เครื่องรัน SWA Agent เป็น root

  2. เครื่องสร้าง key และ CSR ที่มี CN=<node group>; enrolment authority ลงนามด้วย CA ของ server group โดย CA key ไม่เคยออกจาก authority นั้น

  3. Agent ถูกตั้งค่าด้วยชื่อ trust domain, bundle URL ของ tenant (.well-known/ca-bundles), address ของ server, x509pop key และ certificate ของตน และ unix workload attestor

  4. Workload ของ user เดียวกันบนเครื่องนั้นจะได้ SPIFFE ID เดียวกันกับบนเครื่องอื่นทุกเครื่องใน node group (ID แบบ default ไม่มีส่วนของ host) จึงใช้ Secrets Manager host และ permission ร่วมกัน

ความต้องการวิธีการในการออกแบบนี้
แยกแยะแต่ละเครื่องแยก node group (CN ต่างกัน) หรือใช้ SPIFFE ID template ที่มี attribute มากขึ้น; hostname ไม่ใช่ตัวแปร attestor ใน unix attestor (จากรายการตัวแปรที่สังเกตได้จริง)
แยก environmentแยก trust domain + server group + CA (prod, dev) และ authenticator ต่อ environment
Lab host หลายเครื่องบน tenant เดียวLAB_ID ใน config.env: trust domain prod.<LAB_ID>.swa.<domain>, authenticator swa-prod-<LAB_ID>; ทดสอบด้วย lab2 บน Ubuntu 24.04 ควบคู่กับ lab เดิม
Autoscalingออก node certificate ตอน boot จาก PKI/enrolment service (ลงนาม CSR อัตโนมัติ); CA key ไม่ถูกฝังไปกับ image
Agent อยู่หลัง proxyAgent → server เป็น gRPC over TLS บนพอร์ต server API; agent ต้องเข้าถึง addr และ bundle URL ของ tenant ได้
Server บน KubernetesLab นี้: k3s ใน Docker, helm chart ของ vendor, หนึ่ง namespace ต่อ environment, NodePort สำหรับ agent ที่อยู่นอก cluster เนื่องจาก SaaS tenant เข้าถึง cluster ไม่ได้ จึงลงทะเบียน JWKS แบบ inline; cluster ที่มี OIDC issuer ซึ่งเข้าถึงได้จาก public สามารถลงทะเบียน jwks_uri แทนได้ (อนุมาน) Agent ภายใน cluster สามารถใช้ k8s_psat กับ chart swa-agent ของ vendor ได้ (ยังไม่ได้ทดสอบ)

คำแนะนำการตั้งชื่อ: ให้ SPIFFE path บอกว่า workload คืออะไร (environment, node group, service account) ไม่ใช่รันอยู่ที่ไหน เพื่อให้ permission ยังคงใช้ได้เมื่อเปลี่ยนเครื่อง
